# Reference Resolution Semantic Correctness Hardening II

## Objetivo

Executar uma segunda rodada de hardening semântico da resolução nominal COBOL, baseada em lacunas identificadas por review direto do código atual após o primeiro hardening.

Esta tasklist não deve assumir que os bugs descritos realmente existem apenas porque foram identificados por revisão estática.

Para cada hipótese é obrigatório:

regra COBOL
+
fixture adversarial mínima
+
teste automatizado
+
execução contra a implementação atual
↓
prova RED ou refutação da hipótese

Somente depois da prova RED é permitido corrigir o código correspondente.

A abordagem obrigatória é:

HIPÓTESE
↓
FIXTURE
↓
TESTE
↓
RED comprovado
↓
DIAGNÓSTICO DA CAUSA RAIZ
↓
CORREÇÃO GERAL MÍNIMA
↓
GREEN
↓
SUÍTE COMPLETA
↓
COMMIT ISOLADO

======================================================================
REGRAS GERAIS DE EXECUÇÃO
======================================================================

Trabalhar exclusivamente em:

antlr-parse-tree-explorer

Cada fase desta tasklist representa um card independente.

Diferentemente do hardening anterior:

NÃO é necessário pedir autorização ao usuário entre as fases.

Execute todas as fases sequencialmente até a conclusão.

Porém:

CADA FASE DE CORREÇÃO DEVE TERMINAR EM UM COMMIT GIT PRÓPRIO ANTES DE INICIAR A PRÓXIMA.

Não misture correções de problemas diferentes no mesmo commit.

Se durante uma fase for descoberto outro bug pertencente a uma fase posterior:

- registre o achado;
- não antecipe a correção;
- trate-o em sua respectiva fase.

Se surgir um bug novo não previsto nesta tasklist:

- registre-o no relatório;
- crie teste adversarial;
- não o corrija silenciosamente;
- trate-o em uma fase adicional própria, com commit separado.

FASE 1 — GLOBAL EXTERNO NÃO DEVE SER BLOQUEADO POR NOME LOCAL EM PROGRAMA INTERMEDIÁRIO
======================================================================

STATUS: [x] CONCLUÍDA — RED comprovado, correção geral e regressão verdes

Hipótese:

A busca atual para referências DATA não qualificadas pode parar cedo demais quando encontra um nome em um programa intermediário.

Topologia adversarial:

OUTER
│
│ X GLOBAL
│
└── MIDDLE
    │
    │ X LOCAL
    │
    └── INNER
          │
          └── referência X

O X LOCAL de MIDDLE não é visível de INNER.

Ele não deve impedir a busca de alcançar OUTER.X GLOBAL.

Fixture mínima:

Criar algo conceitualmente equivalente a:

PROGRAM-ID. OUTER.

DATA DIVISION.
WORKING-STORAGE SECTION.

01 X GLOBAL PIC X.

PROCEDURE DIVISION.

PROGRAM-ID. MIDDLE.

DATA DIVISION.
WORKING-STORAGE SECTION.

01 X PIC X.

PROCEDURE DIVISION.

PROGRAM-ID. INNER.

DATA DIVISION.
WORKING-STORAGE SECTION.

01 RESULT-X PIC X.

PROCEDURE DIVISION.
    MOVE X TO RESULT-X.

Garantir que a estrutura seja válida segundo a grammar.

Testes obrigatórios:

- comprovar que OUTER.X é GLOBAL;
- comprovar que MIDDLE.X é LOCAL;
- comprovar que INNER não possui X;
- comprovar que INNER → X deve resolver para OUTER.X;
- verificar SemanticEntityId.programUnitId;
- verificar SymbolKind;
- garantir que MIDDLE.X não seja retornado como candidate.

Adicionar controles:

INNER possui X LOCAL
→ deve usar INNER.X

MIDDLE possui X GLOBAL
→ deve usar MIDDLE.X

MIDDLE possui X LOCAL
OUTER não possui X GLOBAL
→ UNRESOLVED

RED obrigatório:

Executar o teste antes da alteração.

Registrar no relatório:

esperado:
RESOLVED → OUTER.X

observado:
...

classificação:
BUG CONFIRMADO / HIPÓTESE REFUTADA

Correção:

Corrigir a lógica de busca por ProgramUnit para distinguir:

nome encontrado no programa da referência

de:

nome LOCAL encontrado em ancestor, portanto invisível

A busca externa deve considerar somente nomes efetivamente participantes da região GLOBAL.

Não implementar uma regra específica para “pular MIDDLE”.

Regressão:

- teste adversarial da fase verde;
- testes de nested visibility anteriores verdes;
- suíte Maven completa verde.

Commit:

fix: harden nested global data lookup

FASE 2 — GLOBAL FILE NÃO DEVE SER BLOQUEADO POR FILE LOCAL INTERMEDIÁRIO
======================================================================

STATUS: [x] CONCLUÍDA — RED comprovado, correção geral e regressão verdes

Hipótese:

resolveFile() pode parar quando encontra um FILE homônimo local em um programa intermediário, mesmo que esse FILE não seja visível no programa interno.

Topologia:

OUTER
│
│ FILE X GLOBAL
│
└── MIDDLE
    │
    │ FILE X LOCAL
    │
    └── INNER
          │
          └── READ X

Resultado esperado:

INNER
↓
MIDDLE.X LOCAL não participa
↓
OUTER.X GLOBAL
↓
RESOLVED

Fixture:

Criar fixture sintética com:

- OUTER.FILE-X GLOBAL;
- MIDDLE.FILE-X LOCAL;
- INNER READ FILE-X.

Adicionar controles:

MIDDLE.FILE-X GLOBAL
→ MIDDLE vence

INNER.FILE-X LOCAL
→ INNER vence

nenhum GLOBAL externo
→ UNRESOLVED

RED obrigatório:

Provar o comportamento da implementação atual antes da correção.

Correção:

Reformular a busca FILE para utilizar uma estratégia nominal coerente com nested program visibility:

local unit
↓
ancestors
   └── somente declarações GLOBAL elegíveis

Não retornar UNRESOLVED simplesmente porque um ancestor possui uma entidade FILE homônima LOCAL.

Regressão:

- fixture nova verde;
- nested-global-file.cbl verde;
- shadowing FILE local existente preservado;
- suíte completa verde.

Commit:

fix: harden nested global file lookup

FASE 3 — FD GLOBAL DEVE TORNAR RECORD-NAMES E SUBORDINADOS GLOBAIS
======================================================================

STATUS: [x] CONCLUÍDA — RED comprovado, correção geral e regressão verdes

Hipótese:

Atualmente:

collectDataEntries(file.entries(), fileScope, false)

pode impedir que GLOBAL do FD seja propagado para os records associados.

Caso:

FD CUSTOMER-FILE GLOBAL.

01 CUSTOMER-RECORD.
   05 CUSTOMER-ID PIC X(10).

Em contained program:

MOVE CUSTOMER-ID TO ...

deve conseguir acessar o nome global herdado.

Fixture:

Criar:

OUTER
└── FD CUSTOMER-FILE GLOBAL
    └── CUSTOMER-RECORD
        └── CUSTOMER-ID

INNER
└── usa:
    CUSTOMER-RECORD
    CUSTOMER-ID

Se aplicável, adicionar:

88 CONDITION
INDEXED BY

subordinados ao record do FD global.

Testes:

Verificar no SymbolTable:

CUSTOMER-FILE   GLOBAL
CUSTOMER-RECORD GLOBAL
CUSTOMER-ID     GLOBAL

e no ReferenceResolution:

INNER.CUSTOMER-ID
→ SemanticEntityId do OUTER

Adicionar controle:

FD local
→ records não são herdados

RED obrigatório:

Provar a falha antes da alteração.

Correção:

Propagar a visibilidade efetiva do FileDescription para a raiz da hierarquia de seus data entries.

A implementação deve reutilizar a infraestrutura existente de effectiveGlobal, não criar uma segunda regra paralela.

Regressão:

- GLOBAL FILE entity continua correta;
- GLOBAL data hierarchy continua correta;
- nova fixture verde;
- suíte completa verde.

Commit:

fix: propagate global fd visibility to records

FASE 4 — FILE RESOLUTION DEVE RESPEITAR SHADOWING NOMINAL ENTRE NAMESPACES
======================================================================

STATUS: [x] CONCLUÍDA — RED comprovado, correção geral e regressão verdes

Hipótese:

A busca de resolveFile() consulta somente FILE entities e pode ignorar uma declaração homônima de outro namespace no programa atual.

Caso adversarial:

OUTER
└── FILE X GLOBAL

INNER
└── DATA X LOCAL

INNER:
    READ X

A busca COBOL nominal deve detectar X no programa da referência.

Não deve ignorar o DATA local apenas porque o statement espera FILE e continuar até OUTER.FILE X.

Fixture:

Construir:

OUTER:
    FD X GLOBAL

INNER:
    01 X PIC X.

    READ X

ou forma sintaticamente válida equivalente.

Adicionar colisões com:

- CONDITION;
- INDEX;
- FILE local;
- DATA local.

Expectativa:

Quando o primeiro nome nominal encontrado não pertence ao namespace permitido:

UNRESOLVED
+
INVALID_NAMESPACE_FOR_CONTEXT

ou reason semanticamente equivalente.

Nunca:

ignorar nome local
↓
resolver FILE global externo

RED obrigatório:

Registrar explicitamente:

nome local:
kind = DATA

nome externo:
kind = FILE GLOBAL

resultado atual:
...

resultado esperado:
...

Correção:

Idealmente reutilizar ou extrair a abstração já introduzida para lookup nominal DATA:

lookup nominal por ProgramUnit
↓
determinação da região de visibilidade
↓
filtragem pelo namespace permitido

Evitar duplicação divergente entre:

DataAndIndexReferenceResolver
CobolReferenceResolver.resolveFile

Mas não fazer redesign grande apenas por estética.

Regressão:

- fixture nova verde;
- GLOBAL FILE existente verde;
- CALL ARGUMENT DATA_OR_FILE continua funcionando;
- suíte completa verde.

Commit:

fix: enforce nominal shadowing in file resolution

FASE 7 — REDEFINES DEVE USAR NÍVEL ESTRUTURAL, NÃO IGUALDADE TEXTUAL DE LEVEL-NUMBER
======================================================================

Hipótese:

A implementação atual exige algo equivalente a:

owner.level == target.level

mas a regra COBOL relevante é estrutural.

Dois itens podem ocupar o mesmo nível hierárquico mesmo quando seus level-numbers escritos são diferentes.

Fixture:

Criar caso válido sintaticamente aceito pela grammar com:

mesmo parent estrutural
+
level numbers diferentes
+
REDEFINES

Exemplo conceitual:

01 GROUP-A.
   05 ITEM-A PIC X.
   04 ITEM-B REDEFINES ITEM-A PIC X.

Usar uma forma COBOL válida segundo a documentação/dialeto adotado.

Adicionar controles:

mesmo número, parent diferente
→ inválido

parent igual, target correto
→ válido

Teste:

Verificar explicitamente:

owner.scopeId == target.scopeId

ou propriedade estrutural equivalente.

Não apenas nomes.

RED obrigatório:

Provar que o filtro textual atual rejeita o caso estruturalmente válido.

Correção:

Usar a hierarquia de scopes como fonte de verdade.

Evitar depender de:

attributes["level"]

para uma propriedade que já está representada estruturalmente.

Regressão:

- testes anteriores REDEFINES verdes;
- targets de outros grupos continuam rejeitados;
- novo caso com level-number diferente verde;
- suíte completa verde.

FASE 8 — CLARIFICAR OCCURRENCE.KIND VS CANDIDATE.KIND PARA SUBSCRIPTS
======================================================================

Hipótese:

Um subscript COBOL pode ser:

INDEX
ou
DATA item

A implementação atual pode produzir:

Occurrence.kind = INDEX
admissibleKinds = {DATA, INDEX}

e depois resolver:

Candidate.kind = DATA

Isso não necessariamente produz binding errado, mas cria um contrato perigoso para o futuro def-use.

Fixture:

Criar:

01 SUBSCRIPT-NUM PIC 9(4).

01 TABLE-X OCCURS 100
   PIC X.

MOVE TABLE-X(SUBSCRIPT-NUM) TO ...

e outro caso:

01 TABLE-X OCCURS 100
   INDEXED BY TABLE-IDX
   PIC X.

MOVE TABLE-X(TABLE-IDX) TO ...

Testes:

Data subscript:

admissibleKinds = {DATA, INDEX}
selected Candidate.kind = DATA

Index subscript:

selected Candidate.kind = INDEX

Objetivo:

Definir explicitamente qual destes contratos queremos:

Opção A:

Occurrence.kind
=
hint/preferred syntactic interpretation

Candidate.kind
=
resolved semantic kind

ou:

Opção B:

reformular o contrato para não fornecer um kind único quando a occurrence é semanticamente polimórfica.

A escolha deve ser documentada.

Critério principal:

O futuro consumidor de ReferenceResolution não pode precisar fazer:

if (occurrence.kind() == DATA)

e acabar ignorando um DATA item usado como subscript.

O resultado resolvido deve fornecer inequivocamente a categoria semântica final.

TDD:

- criar teste antes da mudança;
- provar o estado atual;
- se for apenas ambiguidade de contrato e não bug funcional, registrar claramente;
- alterar somente se necessário para tornar o contrato seguro.

Regressão:

- GLOBAL INDEX continua resolvendo;
- OCCURS INDEXED BY continua correto;
- subscripts numéricos continuam corretos;
- suíte completa verde.

Commit caso haja mudança:

refactor: clarify resolved kind for subscript references

Caso o contrato já seja suficiente e apenas documentação/teste sejam necessários:

test: lock semantic kind contract for subscript references
